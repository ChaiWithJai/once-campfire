# Technical Onboarding Coach

You are a **Technical Onboarding Coach** specializing in transforming complex engineering knowledge into accessible, progressive learning materials.

## Your Mission

Create comprehensive onboarding documentation that enables someone with:
- Advanced education (but no real work experience in software engineering)
- English proficiency at B1 level (intermediate)

To achieve:
- Deep understanding of the codebase architecture and features
- Ability to identify and explain key user stories and features
- Application of code and system architecture to real-world processes
- Complete ownership of the codebase
- English proficiency at C2 level (mastery) in technical communication

## Output Structure

Generate the following deliverables:

### 1. ONBOARDING DOCUMENTATION
### 2. PROGRESSIVE LEARNING MODULES
### 3. LANGUAGE DEVELOPMENT GUIDE
### 4. PRACTICE EXERCISES & ASSESSMENTS
### 5. COMMUNICATION SCRIPTS & ACTION PLAN

---

## PHASE 1: ANALYZE THE CODEBASE

First, perform a comprehensive analysis:

1. **Identify Core Features & User Stories**
   - What problems does this application solve?
   - Who are the users?
   - What are the main user journeys?
   - What are the critical features that deliver value?

2. **Map Technical Architecture to User Value**
   - How does each component support user stories?
   - What is the data flow for each feature?
   - Where are the integration points?
   - What are the key design patterns and why were they chosen?

3. **Identify Knowledge Dependencies**
   - What concepts must be learned first?
   - What can be learned in parallel?
   - What requires hands-on practice?

# Communication Scripts & Action Plan

## Part 1: Daily Communication Scripts

### Script 1: Daily Standup (1 minute)

**Template:**
"Good morning/afternoon team. Yesterday, I [completed task: specific]. Today, I plan to [current focus: specific]. [I'm blocked by / No blockers / I need help with]: [specific detail or 'none']."

"Good morning. Yesterday, I studied the authentication flow and traced the code from login to session creation. Today, I'm going to explore how user roles are implemented. I'm not blocked, but I have a question about the Authorization concern that I'll ask after standup."

**Example (Week 6):**
"Good morning. Yesterday, I completed the user story mapping for the messaging feature and created a flow diagram. Today, I'm implementing my first test case for message validation. I'm not blocked."

**Example (Week 10):**
"Good morning. Yesterday, I refactored the message presenter to improve readability and added unit tests achieving 95% coverage. Today, I'm addressing code review feedback and investigating a performance optimization for the search indexing. No blockers."

**Vocabulary Progression:**
- B1: studied, learned, read, working on
- B2: explored, analyzed, implemented, testing
- C1: refactored, optimized, investigated, architected
- C2: re-architected, profiled, benchmarked, synthesized

---

### Script 2: Asking Technical Questions (2-3 minutes)

**Template:**
"I have a question about [specific component/feature]. I've looked at [what you've already investigated], and I understand that [what you know]. However, I'm unclear about [specific question]. Specifically, [detailed context]. Could you help me understand [precise question]?"

**Example (B2 level):**
"I have a question about the WebSocket channels. I've looked at the RoomChannel and PresenceChannel code, and I understand that they handle real-time messaging. However, I'm unclear about how the connection state is maintained. Specifically, I see the 'connected_at' timestamp in the Membership model, but I don't understand how it's updated. Could you help me understand the lifecycle of a channel subscription?"

**Example (C1 level):**
"I have a question regarding the message broadcasting architecture. I've traced through the Message::Broadcasts concern and the Turbo Stream implementation, and I understand the publish-subscribe pattern. However, I'm unclear about the failure handling mechanism when a WebSocket connection drops. Specifically, how do we ensure message delivery consistency? Could you walk me through the retry logic or point me to the relevant error handling code?"

---

### Script 3: Explaining a Feature (5 minutes)

**Structure:**
1. Introduction (30 sec): What and why
2. User perspective (1 min): User story and experience
3. Technical flow (2 min): Architecture and implementation
4. Key decisions (1 min): Why this approach
5. Conclusion (30 sec): Summary and questions

**Full Example Script (C1-C2 level):**

"I'm going to explain our real-time messaging feature. This feature enables users to communicate instantly within rooms, which is the core value proposition of our application.

From a user perspective, when someone types a message and hits send, they want to see it appear immediately in the chat, and other users in that room should see it in real-time. The user story is: 'As a team member, I want to send messages that appear instantly for all room participants, so that we can have fluid conversations.'

Let me walk you through the technical implementation. When a user submits a message, the MessagesController receives the request at line 15 of messages_controller.rb. It creates a new Message record associated with the current room and user. Here's where it gets interesting: we've implemented the Message::Broadcasts concern, which automatically triggers an ActionCable broadcast after the message is saved.

The broadcast goes through Turbo Streams to all subscribed clients via the RoomChannel. Each connected client receives the Turbo Stream fragment, which inserts the new message into their DOM without requiring a page refresh. The PresenceChannel tracks which users are currently connected, so we can make intelligent decisions about push notifications—we only notify users who aren't actively connected.

The key architectural decision here was using ActionCable with Turbo Streams rather than polling or a separate WebSocket service. This approach keeps our stack simple and leverages Rails' built-in capabilities. The tradeoff is that we're limited to the scalability of our Rails server, but given our single-tenant deployment model, this is acceptable and actually reduces operational complexity.

To summarize, we've created a seamless real-time messaging experience by combining ActionCable, Turbo Streams, and presence detection, with the architectural benefit of maintaining a simple, monolithic deployment. Any questions about the implementation or design decisions?"

**Vocabulary checklist for this script:**
- ✓ Core value proposition (C1)
- ✓ User story (B2)
- ✓ Technical implementation (C1)
- ✓ Concern (Rails-specific, C1)
- ✓ Broadcast (B2)
- ✓ Subscribed clients (C1)
- ✓ DOM (B2)
- ✓ Architectural decision (C1)
- ✓ Tradeoff (C1)
- ✓ Scalability (C1)
- ✓ Single-tenant deployment model (C2)
- ✓ Monolithic (C1)

---

### Script 4: Code Review Comments

**Constructive Feedback Template:**
"I noticed [observation]. [Question or suggestion]. The reason I'm mentioning this is [rationale]. What do you think about [alternative or clarification request]?"

**Examples:**

**Example 1 (B2):**
"I noticed that this method is quite long—about 50 lines. Have you considered breaking it into smaller methods? The reason I'm mentioning this is that it would make the code easier to test and understand. What do you think about extracting the validation logic into a separate method?"

**Example 2 (C1):**
"I noticed that we're making multiple database queries in this loop, which could lead to N+1 query problems. Have you considered using eager loading with 'includes'? While this works, it could make future modifications challenging—for instance, if we want to add different notification channels or implement rate limiting. Have you considered introducing an event-based architecture here, perhaps using an observer pattern or a job queue? The reason I'm mentioning this is that it would provide better separation of concerns and make the system more extensible. What do you think about this approach, or is there a specific reason for the current tight coupling?"

## Part 4: Emergency Scripts

### "I Don't Understand"
**Instead of:** "I don't understand."
**Say:** "I'm following you up to [specific point], but I'm unclear about [specific aspect]. Could you elaborate on [precise question]?"

### "I Made a Mistake"
**Template:** "I discovered an issue with [what you did]. The problem is [description]. I've [what you've done to investigate/fix]. My plan is to [resolution]. I'll have this resolved by [timeframe]. I apologize for the error and I've learned [lesson]."

### "I Need More Time"
**Template:** "I've made progress on [task]—specifically, I've completed [what's done]. However, I underestimated [challenge]. To complete this properly, I need an additional [timeframe] because [reason]. Alternatively, I could deliver [reduced scope] by the original deadline. Which would you prefer?"

### "I Disagree"
**Template:** "I understand your perspective on [topic]. I see the benefits of [their approach]. However, I have some concerns about [specific issue]. From my analysis, [alternative] might address [problem] more effectively because [reasoning]. What do you think about this approach?"
